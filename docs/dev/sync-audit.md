# Readerr sync audit — findings catalogue

Generated by a multi-agent audit (8 dimensions, adversarial verification). The reconciliation dimension was fully verified before a session usage limit interrupted the remaining verifiers; unverified findings are grounded in cited code and were spot-checked while building the harness. Each finding below is a candidate for a red-before/green-after case in the [harness](../../sync-testing-framework.md).

**Severity split:** data-loss 22 · critical 12 · major 28 · minor 12 · design-smell 4 — 78 total.

## DATA-LOSS (22)

### D1. Server reconcileWeeks between push chunks tombstones a stray week before its week_links arrive — entries orphaned forever on server and every client

- **Location:** `backend/sync.go:243`
- **Mechanism:** handlePush runs reconcileWeeks at the end of EVERY push transaction (sync.go:243). The client splits large pushes into PUSH_CHUNK=2000-row requests (sync.ts:265), and the dirty array is ordered by STORES (weeks store precedes week_links, types.ts:189-203), so a chunk boundary can put a week in request k and its week_links in request k+1. The fold in request k sees the duplicate open week WB with zero entries, tombstones it (sync.go:383-385) and re-points nothing. Request k+1 then INSERTs WB's entries (no existing row → no LWW skip) pointing at the now-tombstoned WB. Neither reconciler ever heals this: server fold selects only 'deleted_at IS NULL AND closed_at IS NULL' weeks (sync.go:290), and client reconcileOpenWeeks iterates only live weeks via all() (weeks.ts:56-63) — entries of a tombstoned week are never re-pointed by anything. The same failure occurs when a push fails mid-chunk and the retry happens after another device's push triggered the fold ('idempotent under LWW' comment at sync.ts:262 is false across the parent/child chunk boundary).
- **Two-device scenario:** Device A creates week WA for Monday and syncs. Device B, offline all week with a large un-synced dataset (initial sync, >2000 rows), mints twin WB for the same Monday and schedules 8 links onto it. B syncs: chunk 1 carries WB (plus links/tags…), server folds WA+WB → WB tombstoned; chunk 2 carries WB's 8 week_links → inserted pointing at dead WB. B then pulls the WB tombstone → its reading week vanishes locally; A pulls the 8 entries → invisible (weekEntries/pendingWeeksForLink resolve the week via get(), which filters tombstones). The 8 scheduled entries (kind, done_at, positions) are permanently unreachable on server and both devices.

### D2. Server pull reads each table in a separate implicit transaction: a push committing mid-pull makes latestSeq jump over rows the client never received

- **Location:** `backend/sync.go:435`
- **Mechanism:** handlePull iterates tableOrder issuing one `s.db.Query(...)` per table (line 435) directly on the pool — 13 independent read snapshots, not one transaction. A concurrent handlePush commits atomically between two of those queries. If the push's transaction wrote a row into an already-scanned table (e.g. links, table 3) and another into a later table (e.g. week_links, table 13) with consecutive seqs, the pull misses the links row (its query ran pre-commit) but returns the week_links row (query ran post-commit). latestSeq (lines 473–484) is the max seq among returned rows, so it includes the higher seq; the client stores it as lastPullSeq (sync.ts:328–329) and every future pull asks `server_seq > latestSeq` — the skipped links row sits below the cursor forever. It is only re-delivered if some later edit re-stamps it with a new seq. Cross-table sibling writes with adjacent seqs are the norm (capture writes links+link_tags+week_links; reconcileWeeks rewrites weeks+week_links), and push-during-pull is routine with two devices auto-syncing on page loads.
- **Two-device scenario:** Device A captures a link with a week assignment and syncs: its push transaction inserts links row L (seq 501) and week_links row E (seq 502), committing at time t. Device B's auto-sync pull had already executed the `links` SELECT at t-5ms (cursor since=500, saw nothing) and executes the `week_links` SELECT at t+5ms, receiving E. B's response has latestSeq=502; B stores lastPullSeq=502 and applies E. B now permanently lacks L: the reading-list entry E references a link B doesn't have (weekEntries silently drops it), and every subsequent pull starts above seq 501. L only appears on B if A ever edits L again.

### D3. LWW rides raw client wall-clocks with no server time authority: a slow-clock device's edits and deletions are silently discarded and deletions resurrect

- **Location:** `backend/sync.go:210`
- **Mechanism:** Every conflict decision is a string compare of client-stamped updated_at: server push skips when `updatedAt <= existing` (backend/sync.go:210), client pull overwrites when `row.updated_at >= local.updated_at` (sync.ts:322), and all stamps come from `new Date().toISOString()` on whichever device wrote (repo.ts:10,72,80,90). No component ever consults server time for ordering. Consequences: (a) a device whose clock runs N minutes slow loses every conflict against edits made up to N minutes earlier in real time — its push is skipped and the very next pull overwrites its local copy, so the user watches their own change revert with no error; (b) softDelete stamps the tombstone with the slow clock (repo.ts:90), so the tombstone loses to the row's existing server updated_at: the push is skipped and the pull resurrects the deleted item on the device that deleted it — repeatably; (c) the heal-path re-stamps that exist specifically to force redelivery — reconcileOpenWeeks' `put('weeks', survivor)` (weeks.ts:95) and dedupePairs' survivor re-put (repo.ts:162) — produce an updated_at that can be ≤ the server's stored value on a slow-clock device, so the server skips the re-pushed survivor, no new server_seq is assigned, and devices whose cursors passed the original seq still never receive the row the fold pointed everything at (the empty-week bug those comments describe as fixed). The server-side reconcileWeeks backstops (c) for weeks only; junction pairs have no server backstop.
- **Two-device scenario:** Device B's clock is 5 minutes behind. Device A edits note N at real 12:00 (stamp 12:00). At real 12:03, B rewrites the same note (stamp 11:58) and syncs: push is skipped (11:58 <= 12:00), pull applies A's row (12:00 >= 11:58) — B's newer-in-reality edit is destroyed on B's own screen minutes after typing it. Separately, B deletes link L at real 12:04 (tombstone 11:59) while the server holds L at 12:00 from A: the tombstone never uploads and the pull revives L on B; the link the user deleted keeps coming back on every sync until B's clock passes A's last-edit stamp.

### D4. Onboarding 'Start from scratch' (and 'Skip the rest'/finish) on a server-served install mints a fresh settings singleton that clobbers the synced settings on every device

- **Location:** `frontend/src/components/apps/OnboardingApp.svelte:180`
- **Mechanism:** startFromScratch (OnboardingApp.svelte:179-182) and finish (163-177) call saveUserSettings, which creates the settings row at the FIXED singleton id 'readerr-user-settings' with all-default values and updated_at=now (settings.ts:100-119). In the normal Docker posture the app is served by the sync backend: getSyncUrl() defaults to same-origin (sync.ts:42) and getSyncMode() defaults to 'sync' (sync.ts:52-54), so no configuration step is needed for sync to be live. After the redirect to '/', Navbar fires maybeAutoSync (Navbar.svelte:14) → syncNow pushes BEFORE pulling (sync.ts:244-295) → the brand-new defaults row is strictly newest anywhere, so the server's LWW accepts it and replaces the real settings (sync.go:210 passes: newer). The conflict-resolution machinery never engages: it only exists in SettingsApp.saveSyncUrl, and localHasData() deliberately ignores user_settings ('The settings row alone doesn't count', sync.ts:173-180), so nothing classifies this as a both-sides-have-data situation.
- **Two-device scenario:** Household server serves readerr; device A has months of tuned settings synced (quota 5, three focus tags, strip mode 'all' + whitelist, archival on). New device B opens http://server:8080, sees onboarding, and its user clicks 'Start from scratch' (a top-level Welcome button). B stamps a defaults singleton at the fixed id, lands on '/', auto-sync pushes it; the server row is overwritten (quota null, focus tags [], strip off, archival off). A's next sync pulls the defaults — every carefully tuned setting is gone on all devices, with no prompt and no way back but manual reconfiguration.

### D5. Full-restore import drops lastPushAt but keeps lastPullSeq/serverEpoch — restoring an older backup silently forks the device from the server forever

- **Location:** `frontend/src/lib/db/export.ts:227`
- **Mechanism:** importData's post-import bookkeeping is only `await db.delete('sync_meta', 'lastPushAt')` (export.ts:226-228). lastPullSeq and serverEpoch survive the restore, and the imported rows keep their historical server_seq. On the next syncNow: (push) the dropped lastPushAt makes the dirty scan send every restored row, but the server's LWW gate `if existing.Valid && updatedAt <= existing.String { continue }` (backend/sync.go:210) rejects all of them — every row is equal-or-older than the server's current copy — so the restore never reaches the server; (pull) `since = lastPullSeq` (sync.ts:301) is still the pre-restore high-water mark, and handlePull only returns `server_seq > since` (sync.go:426), so every server row the restore rewound past — including tombstones for rows the backup resurrects — sits below the cursor and is never re-delivered. The epoch guard (sync.ts:224-228) doesn't fire because the epoch didn't change. No error is surfaced; lastSyncAt updates as if healthy. Worse, any row the user subsequently edits on the restored device gets updated_at=now and DOES push, splicing single backup-era rows into the server's newer dataset. docs/user/sync-and-backups.md sells this exact file as 'your disaster-recovery file' whose import 'replaces all local data' — on a synced device the restore is silently inert against the server. Fix requires deleting lastPullSeq (and arguably nulling imported server_seq) on full replace.
- **Two-device scenario:** Device A and B sync via server S. Monday: A exports a full backup. Both devices keep working through Friday (server seqs reach 900; A's lastPullSeq=900). Friday: A imports Monday's backup to undo a bad week. Restore succeeds locally; next sync reports success (pushed 0 accepted, pulled 0). A now shows Monday's data indefinitely while B and S show Friday's — links deleted since Monday are resurrected on A only, notes edited since Monday are stale on A only. When A then favourites one restored link, that Monday-era row (fresh updated_at) pushes and overwrites S's Friday copy; B pulls it and loses its Friday edits to that row. The two datasets interleave irreversibly with no error ever shown.

### D6. Merge-mode import (curated/range/template) blindly puts rows by id with no LWW check — regresses newer local rows and resurrects deletions, then poisons the network on next edit

- **Location:** `frontend/src/lib/db/export.ts:216`
- **Mechanism:** For non-full scopes importData does `store.put(row)` unconditionally (export.ts:215-217) — no comparison against the existing row's updated_at, and no check of deleted_at. An older exported copy therefore overwrites a strictly newer local row (including overwriting a newer local tombstone with an older live row — resurrection). The subsequent lastPushAt drop (line 227) makes the stale rows push, but the server rejects them as older (sync.go:210), and pull never re-delivers the newer server copies because they are below lastPullSeq. The header comment's guarantee (line 15-16: 'partial exports can never wipe a fuller dataset') and SettingsApp's confirm text (SettingsApp.svelte:364: 'merged into your existing data (nothing is deleted)') are both violated: rows aren't removed, but their content is rolled back and deletions are undone.
- **Two-device scenario:** Device A edits note N Monday and syncs; device B pulls it. Tuesday B imports a curated export taken last week (it contains N's old body). B's newer N is overwritten in place. B's next sync: push offers stale N, server rejects (older); pull returns nothing (N's newer seq already below B's cursor) — B permanently displays last week's note while A and the server hold Monday's. When B later opens that note and the editor autosaves, the week-old body gets updated_at=now, pushes, wins LWW on the server, and A pulls it — Monday's edit is destroyed on every device. Same shape for tombstones: a link_tag B deleted after the export is resurrected locally by the import and, on any touch, network-wide.

### D7. Full-backup restore keeps lastPullSeq: documented disaster-recovery flow permanently diverges a synced device

- **Location:** `frontend/src/lib/db/export.ts:227`
- **Mechanism:** docs/dev/sync.md:151-162 and docs/user/sync-and-backups.md:113-114 present 'Export JSON … importing one replaces all local data. This is your disaster-recovery file', and sync.md claims the only sync interaction is that importData 'drops the push cursor … the next sync re-scans and re-pushes everything once, and the server LWW-ignores whatever it already has.' The code does exactly and only that: importData deletes 'lastPushAt' (export.ts:226-228) but never touches 'lastPullSeq' or 'serverEpoch' (sync_meta cannot even be in the envelope: fullData() iterates STORES+LOCAL_STORES only, export.ts:43, and importData filters names to that same set, export.ts:206-207). After restoring an older backup on a device that had already synced, push sends the backup's stale rows and the server's strict-newer LWW (backend/sync.go:210) skips them all, while pull runs with the pre-restore high-water mark (sync.ts:301), so every server row at seq <= lastPullSeq — i.e. everything that changed or was created between backup time and now — is never re-delivered. syncNow then records lastSyncAt/ok (sync.ts:334-336). Nothing in normal operation ever heals this (only an epoch rotation or server switch would).
- **Two-device scenario:** Devices A and B sync via server S; A exports a full JSON backup in January. By June both devices and S share newer data (edited notes, 200 new links) at seq ~900. A bad bulk edit happens; the user restores January's backup on A as the docs advise. A's next sync: push re-sends the January rows, S LWW-skips every one; pull?since=900 returns nothing; sync reports success. Permanently: A shows January data, B and S show June data; links captured on B in spring never appear on A; A's 'recovered' values never reach B or S. Both devices report healthy syncs forever while holding different datasets.

### D8. Merge-scope imports blind-put stale rows over newer data, then LWW+cursor pin the regression: 'partial exports can never wipe a fuller dataset' is false

- **Location:** `frontend/src/lib/db/export.ts:216`
- **Mechanism:** export.ts:15-17 documents 'Importing anything but a full backup MERGES rows in by id — nothing is cleared — so partial exports can never wipe a fuller dataset', and docs/user/sync-and-backups.md:121-122 markets curated/range/template exports as 'mergeable slices'. The merge path (export.ts:212-218) does a raw store.put(row) per row with no updated_at comparison — an old exported row (curated/range/template rows carry their historical updated_at and server_seq, captured by db.getAll at export time) wholesale overwrites a strictly newer local row of the same id. importData then drops only lastPushAt (line 227), so the next push re-sends the regressed rows, the server's strict-newer LWW (backend/sync.go:210) rejects them, and the pull cursor (still at the current high-water mark) never re-delivers the server's newer copies — the regression is pinned locally and diverges from the fleet, exactly the trap of the finding above but reachable through the 'safe' merge import.
- **Two-device scenario:** Device A exports a curated JSON in January (tags, topics, notes included). Through June, A and B keep editing those same tag documents and notes; everything syncs. In June the user re-imports the January curated file on A ('merging is safe — nothing is cleared'). Every tag/topic/note row present in the file reverts on A to its January content; A's push is LWW-skipped by the server; A's pull cursor is past those rows' seqs so the June versions never come back. A permanently shows January prose for those rows while B and the server show June — silent divergence with data visibly regressed on one device.

### D9. Archive hard-deletes live synced rows without tombstoning — links resurrect, duplicate, and stale copies clobber newer edits

- **Location:** `frontend/src/lib/services/archive.ts:59`
- **Mechanism:** archiveNow() does `tx.objectStore('links').delete(link.id)` (hard delete, no tombstone) and copies the row to local-only `archived_links`. The row stays LIVE on the server. Three consequences: (1) any later change to that row on another device gives it a new server_seq; this device's pull hits `!local` in sync.ts:322 and re-INSERTs it into `links` while the stale copy still sits in `archived_links` — the link now exists in both stores. (2) `unarchive()` (line 68) does `put('links', {...link})` which re-stamps updated_at on the months-old archived snapshot, so it wins LWW over any newer server-side version and overwrites it everywhere. (3) capture-time URL dedupe (capture.ts:297 `byIndex('links','url',url)`) can't see archived rows, so re-capturing an archived URL mints a second live UUID for the same URL server-wide. (4) An epoch change (checkServerEpoch → resetLocalSyncState → pull from seq 0) re-delivers EVERY archived link into the hot store en masse, duplicating the whole archive.
- **Two-device scenario:** Device A archives link L (slushed 25 months ago): L hard-deleted from A's links, copied to A's archived_links. Device B hasn't archived yet; user favourites L on B (clears slushed_at, fresh updated_at, new server_seq). A pulls: L reappears in A's backlog/favourites AND still shows in A's Archive tab — two copies of one link. User later clicks Unarchive on A: unarchive() puts the stale archived snapshot (favourite=false, slushed_at set, fresh updated_at) into links; A pushes; B pulls; the favourite is silently erased on every device.

### D10. Title fetch writes a whole-row link snapshot captured before sync pull: a resolved title reverts the other device's edits and wins LWW globally

- **Location:** `frontend/src/lib/services/capture.ts:363`
- **Mechanism:** fetchTitle holds a `link` row snapshot for up to ~1.2s (3 attempts × 400ms, lines 358–371) plus network latency, then writes the ENTIRE snapshot back: `put<Link>('links', { ...link, title, title_fetched: true })` (line 363). put re-stamps updated_at = now (repo.ts:72), so whatever the snapshot contains becomes the newest version of the row everywhere. retryMissingTitles (lines 399–404) snapshots via `all<Link>('links')` on every Backlog mount — the same mount where Navbar has just fired maybeAutoSync. If the pull applies another device's newer link row (read_at, favourite, slushed_at, priority changes) between the snapshot and the title resolution, the put overwrites it with the pre-pull field values under a fresh timestamp; the next push propagates the reverted row to the server and every device. The same clobber hits a local edit made during the fetch window.
- **Two-device scenario:** Device B reads link L (captured offline on A, so title_fetched=false), marks it read and favourite, and syncs. Device A comes online and opens the Backlog: retryMissingTitles snapshots L (read_at=null, favourite=false) and starts GET /title; concurrently maybeAutoSync's pull applies B's row (read_at set, favourite=true). 600ms later the title resolves and A writes {...snapshot, title, title_fetched:true} with updated_at=now — read_at=null and favourite=false again, but timestamped newer than B's edit. A's next push wins LWW on the server; B pulls its own read/favourite state reverted. The only surviving trace of B's action is nothing — both devices now agree L was never read.
- **FIXED:** fetchTitle now writes through `repo.patch()` — re-read the row, set only `title`/`title_fetched`. A row that already reads `title_fetched` is left alone (another device, or the user via `renameLink`, has settled an authoritative title), and a link deleted mid-fetch is skipped rather than resurrected. Guards: the "background title fetch" cases in `frontend/test/staleSnapshot.test.ts`.

### D11. Reconcile-on-read folds stamp fresh updated_at onto stale content, permanently clobbering concurrent genuine edits (note bodies, topic documents, tag notes, plan fields, settings)

- **Location:** `frontend/src/lib/services/notes.ts:41`
- **Mechanism:** Every fold rewrites the survivor through put(), which re-stamps updated_at to now (repo.ts:72). The folded content, however, is computed only from the folding device's LOCAL copies (freshest() over its rows). A device that still holds pre-fold duplicates (because it hasn't pulled the other device's tombstones yet) re-runs the fold later and writes OLD content under a NEWER timestamp. Under strict LWW (server handlePush sync.go:210 'updatedAt <= existing' skip; client pull sync.ts:322 'row.updated_at >= local.updated_at' apply) this stale-content/fresh-stamp row beats the other device's genuinely newer edit, and the losing edit is never re-pushed (its row is no longer dirty above lastPushAt). Same pattern at links.ts:115 (reconcileTags → tags.notes_md), links.ts:135 (reconcileTopics → topics.body_md, the flagship long-form document), plans.ts:80-87 (reconcilePlans → all plan fields), settings.ts:38 (getUserSettings collapse → whole settings row).
- **Two-device scenario:** Both devices hold duplicate note rows N1/N2 for link L (created offline on each, then fully synced). Device B opens the note editor → getNote folds (keeps N1, tombstones N2), then B writes a paragraph into N1 (updated_at = 10:00). Device A went offline BEFORE B's fold synced, so A still holds live N1+N2. At 10:05 A merely opens the same link's note page → getNote at notes.ts:41 re-puts N1 with A's stale body under updated_at = 10:05, tombstones N2. A syncs: server accepts stale-body N1 (10:05 > 10:00); B pulls it (10:05 ≥ 10:00) and its local edit is overwritten. B's paragraph is gone on every device and on the server — no copy survives anywhere.

### D12. Client reconcileOpenWeeks racing a paged/in-flight pull tombstones a just-pulled week before its entries arrive, then pushes the tombstone — the other device's whole week disappears everywhere

- **Location:** `frontend/src/lib/services/weeks.ts:85`
- **Mechanism:** syncNow applies pulled rows store-by-store with awaited single-op IDB puts (sync.ts:315-327) and pages by global seq (weeks rows carry smaller seqs than their week_links, so they can land in an earlier page or earlier in the same page). reconcileOpenWeeks runs from every week-page read (findWeek/ensureWeek/ensureOpenWeek/autoCloseStaleWeeks) and can interleave between those awaits. If the local twin WB has the smaller id, the fold picks WB as survivor and soft-deletes the just-pulled WA (weeks.ts:85) after re-pointing WA's entries via byIndex — which finds NOTHING because WA's entries haven't been applied yet (weeks.ts:75). The entries then arrive pointing at a locally-tombstoned WA. The tombstone carries a fresh nowIso() stamp, so the next push wins server-side LWW (sync.go:210), WA dies on the server, and no reconciler ever re-points entries of a dead week (see previous finding's mechanism).
- **Two-device scenario:** Device A has open week WA (id 'f3…') with 6 entries, all synced. Device B, offline, minted twin WB (id 'a1…' < WA) for the same Monday. B comes online; auto-sync starts pulling while B has the /week page open. Pull applies WA; a UI-triggered ensureOpenWeek fires before WA's 6 week_links rows are applied → fold keeps WB, soft-deletes WA (fresh stamp), finds no WA entries to re-point. The 6 entries then apply, orphaned under dead WA. B's next push tombstones WA on the server; A pulls it → A's entire reading week (6 entries, done flags, order) vanishes on A, B, and the server permanently.

### D13. Week folds drop the stray's duplicate entry wholesale — done_at/kind on the tombstoned twin entry is silently lost (no mergeSurvivor for week_links)

- **Location:** `frontend/src/lib/services/weeks.ts:79`
- **Mechanism:** When a stray week's entry references a link the survivor already holds, both the client fold (weeks.ts:76-80 'survivor's wins') and the server fold (sync.go:365-368) tombstone the stray entry without merging any of its state onto the survivor's entry. Unlike dedupePairs' mergeSurvivor hook (repo.ts:134, used by link_topics to keep ref_number), week_links carry real user state — done_at, kind ('review' vs 'reading'), and potentially outcome — and the dropped duplicate may be the only row carrying it. The surviving entry keeps done_at = null, and LWW then propagates that everywhere.
- **Two-device scenario:** Devices A and B both offline ensureWeek() the same Monday: A mints WA (smaller id), B mints WB. Both schedule link L; B reads the article and marks it done (done_at stamped on WB's entry). B syncs: server reconcileWeeks keeps WA as survivor, sees WA already holds L (seen[e.linkID], sync.go:365), tombstones WB's done-stamped entry. The merged week shows L not-done on every device; B's completion is gone. At week close the entry is stamped 'rolled' instead of 'read'/'slushed' — the reading history permanently records the article as never finished.

### D14. autoCloseStaleWeeks closes weeks from stale local state before the first pull, overwriting the other device's completions and outcomes

- **Location:** `frontend/src/lib/services/weeks.ts:384`
- **Mechanism:** WeekApp.svelte:208 runs `await autoCloseStaleWeeks()` in init() on mount, while Navbar.svelte:14 fires maybeAutoSync() fire-and-forget in parallel — there is no ordering guarantee that the pull lands first, and after >15min offline there is guaranteed un-pulled remote state. closeWeek stamps every entry with `put('week_links', {...entry, outcome:'rolled'})` (line 384) based purely on the LOCAL entry.done_at / link.read_at, giving each row a fresh updated_at. When the pull then arrives, sync.ts:322's LWW check (`row.updated_at >= local.updated_at`) rejects the other device's older-stamped done_at/outcome rows, and the next push propagates the wrong 'rolled' stamps to the server and every device.
- **Two-device scenario:** Device B reads 8 links during the week, entries get done_at; B closes the week Sunday night — outcomes 'read'/'slushed' on the server. Device A was offline all week (its copy of the week is still open, entries done_at=null). Monday, A comes online and opens /week: autoCloseStaleWeeks re-closes the week from A's stale state, stamping all 8 entries outcome='rolled', done_at=null with fresh timestamps. A pushes; B pulls; the entire week's reading history is rewritten to 'rolled' everywhere. The links rows (read_at/slushed_at, which A never touched) keep B's values, so the data is also self-contradictory: links slushed by a close whose entries say they were never finished.

### D15. Pulled remote rows re-enter the dirty scan and poison the lastPushAt watermark under clock skew, permanently stranding local edits

- **Location:** `frontend/src/lib/sync.ts:257`
- **Mechanism:** Pull applies remote rows verbatim, preserving the remote device's updated_at (line 324 `db.put(store, row)`). The next syncNow's dirty scan is purely `updated_at > lastPushAt` on the index (line 254) — there is no per-row dirty flag — so freshly pulled remote rows re-enter `dirty`, and line 257 (`if (row.updated_at > maxPushedUpdatedAt) maxPushedUpdatedAt = row.updated_at`) folds the REMOTE timestamp into the watermark, which line 296 persists as lastPushAt. If the remote device's clock is ahead, lastPushAt now sits in this device's future. Every local edit stamped by repo.ts nowIso() (repo.ts line 72) until real time passes that watermark has updated_at < lastPushAt, is excluded by the exclusive lower bound (line 248), and is never pushed. The doc-promised server_seq==null rescue does not exist in code, so nothing ever recovers them.
- **Two-device scenario:** Device B's clock is 3 minutes ahead (no NTP on the LAN). B edits a note at B-time T and syncs. Device A syncs and pulls that note (updated_at = A-now + 3 min). A syncs again: the pulled note is 'dirty', so A sets lastPushAt = T (3 min in A's future). During the next 3 minutes A favourites link L and captures a new link M (server_seq null). Neither ever qualifies for the dirty scan — L's toggle and M are never pushed, ever. B never sees M; later B touches L and A's pull (row.updated_at >= local) silently reverts A's favourite. M exists only on A; if A ever runs 'replace local with server', M is gone everywhere.

### D16. Watermark computed from a non-atomic snapshot with an exclusive lower bound strands edits written during/after the dirty scan at <= max timestamp

- **Location:** `frontend/src/lib/sync.ts:296`
- **Mechanism:** The dirty scan (lines 253-259) awaits per store across 13 stores, then the push phase awaits network fetches, and only then line 296 writes lastPushAt = max updated_at of the SNAPSHOT. Any write committed after its store was scanned but timestamped <= that max is skipped this sync AND excluded from all future scans, because line 248 uses IDBKeyRange.lowerBound(lastPushAt, true) — exclusive — and rows strictly below the watermark never match. Concretely reachable two ways: (a) a multi-store user action (or a second tab) writes store links at millisecond M after links was scanned, while week_links — scanned later — receives a row at M, making the watermark >= M; (b) an edit lands after the scan in the same millisecond as maxPushedUpdatedAt (equality is excluded by the exclusive bound). The stranded edit is never pushed until the user coincidentally edits the same row again.

### D17. Header-comment-promised 'server_seq == null' push rescue does not exist — never-accepted rows below the watermark are permanently stranded

### D18. server_seq write-back is a non-atomic read-modify-write that can revert a concurrent user edit to the pre-push snapshot

### D19. Pull apply's LWW check and put are non-atomic; combined with the self-echo of just-pushed rows, every sync can clobber concurrent local edits with older server rows

Device A (Firefox on Linux, NetworkManager marks the network 'limited') captures and edits for weeks: maybeAutoSync returns at line 365 on every page load, nothing is pushed, and the sync history shows no attempts at all. Device B, on a browser that reports onLine=true, syncs normally and never sees A's data. The divergence only closes when the user happens to press the manual Sync button on A — which works instantly, deepening the confusion.

### M10. maybeAutoSync consumes its session flag and 15-minute budget before the sync runs, so one failed attempt suppresses auto-retry

- **Location:** `frontend/src/lib/sync.ts:370`
- **Mechanism:** Lines 370–372 set SESSION_SYNC_KEY and AUTO_SYNC_AT_KEY, then fire `void syncNow()` — the throttle state is committed regardless of outcome. If that syncNow fails (server restarting, transient DNS/socket error at app-open, the one moment auto-sync always fires), the session flag plus the fresh timestamp make every subsequent page navigation return early at line 369 for the next 15 minutes. There is no online-event or failure-triggered retry anywhere (Navbar's online listener only flips the badge), so a device that opened the app during a 5-second server blip silently syncs nothing for 15 minutes of active use.
- **Two-device scenario:** The user reboots the machine hosting the Go backend and, 3 seconds later, opens readerr on device A: the session-start auto-sync fails instantly (connection refused) but stamps both throttle keys. The user then spends 10 minutes capturing links and navigating — every mount hits the 15-minute guard and skips. Device B, opened later, syncs fine but sees none of A's session until A crosses the 15-minute mark or the user manually syncs; meanwhile edits to the same rows on B accrue newer timestamps and will win LWW over A's still-unpushed earlier work.

### M11. Timestamp-tie asymmetry: pull's >= silently discards an unpushed local edit that ties with a remote row — the documented 'most recent edit wins' has an undocumented losing case

- **Location:** `frontend/src/lib/sync.ts:322`
- **Mechanism:** sync.md:17-19 and sync-and-backups.md:14-16 describe conflict handling purely as 'the most recent edit wins'. The server keeps its copy on a tie (`updatedAt <= existing` skips, sync.go:210) while the client overwrites on a tie (`row.updated_at >= local.updated_at` applies, sync.ts:322). I verified this pair does converge (both devices end on the first-pushed copy — the doc's 'everyone converges' claim holds), but on an exact millisecond tie between two different edits of the same row on two devices, the second pusher's edit is skipped by the server AND its local copy is then overwritten by the pulled tie row — the edit vanishes without ever being 'less recent'. Ties require the same row id written in the same millisecond on both devices, so real-world frequency is very low; reporting because the hunt list names exactly this asymmetry and the edit is unrecoverable when it fires.
- **Two-device scenario:** Devices A and B both edit note N (same row id) at exactly 2026-07-24T10:00:00.123Z — A sets body 'alpha', B sets 'beta'. A syncs first: server stores 'alpha'. B pushes: '…123Z' <= '…123Z' → skipped, not accepted. B pulls: row.updated_at >= local.updated_at → 'alpha' overwrites B's 'beta'. Both devices converge on 'alpha'; B's edit is gone although it was not older, and no doc mentions that a tie exists or which side loses.

### M12. Same-millisecond edits at the push watermark are permanently skipped by the exclusive dirty-scan lower bound

- **Location:** `frontend/src/lib/sync.ts:247`
- **Mechanism:** lastPushAt is set to the max updated_at among scanned rows (line 295) and the next scan uses IDBKeyRange.lowerBound(lastPushAt, true) — exclusive. nowIso() has millisecond precision (repo.ts:10), so a row written after the dirty scan but within the same millisecond as maxPushedUpdatedAt (e.g. a bulkPut capture racing the scan, or a put on a machine stamping the identical ms) compares equal, falls outside the range, and is never pushed until the row is edited again. (Overlaps the sync-loop dimension; the write-path contribution is bulkPut stamping many rows with one nowIso wall-clock ms.)
- **Two-device scenario:** Auto-sync's dirty scan runs on A while the user pastes a batch; one captured link is stamped in the exact millisecond that becomes lastPushAt but lands after the scan read its store. That link never appears on device B (and never errors) until the user happens to edit it on A.

## DESIGN-SMELL (4)

### D1. Migrated server DBs keep unsynced legacy focus_tag_id columns whose carried-over value is destroyed by the first replace — fresh vs migrated schema drift

- **Location:** `backend/db.go:86`
- **Mechanism:** The v6→v7 migration (db.go:86-89) adds focus_tag_ids and copies the old value in, but leaves focus_tag_id in place on user_settings and plans ('the old columns stay in place but are no longer synced'). A fresh schema.sql database has no such column, so migrated and fresh servers permanently differ in shape — the one real divergence in an otherwise fully verified 16-step migration chain (diffed against the true v1 schema from git 21a778d; every other column, CHECK, index, and the sync_state epoch match exactly). Because handlePush uses INSERT OR REPLACE naming only the tables-map columns (sync.go:230), the first accepted push of a settings/plan row deletes the old row and re-inserts it with focus_tag_id reverted to NULL — the migrated historical value survives only until the row is first replaced, so the two schemas also diverge in data, not just shape.
- **Two-device scenario:** A long-lived server DB is migrated to v7+; user_settings.focus_tag_id='tag-abc' was copied into focus_tag_ids. Device A pushes any settings change: INSERT OR REPLACE re-creates the row with focus_tag_id NULL. Consequence today is nil (nothing reads the column server-side), but any future rollback to a pre-v7 binary, or forensic recovery from the sqlite file, finds the legacy column silently emptied — and fresh-vs-migrated servers can no longer be compared table-shape-equal in tooling.

### D2. No sync is triggered after any mutation — changes wait for a navigation-gated, 15-minute-throttled auto-sync, widening every LWW race above

- **Location:** `frontend/src/components/Navbar.svelte:14`
- **Mechanism:** Verified: syncNow is called only from SettingsApp (manual/conflict flows), OnboardingApp (restore), and Navbar's maybeAutoSync — which runs only on page mount, once per session, then at most every 15 minutes (sync.ts:364-373). No mutation path pushes, there is no interval timer, and nothing flushes on pagehide/beforeunload. A tab left open never syncs again; edits made just before closing the app may never push at all. This is the enabling condition for the autoCloseStaleWeeks clobber (a Sunday-night completion that never pushed is 'rolled' by Monday's other-device auto-close) and stretches every stale-snapshot window from milliseconds to hours.
- **Two-device scenario:** User finishes the week's reading on the phone Sunday evening and closes the browser — the done_at stamps sync never pushed. Monday at the desk, /week auto-closes the stale week: every entry is stamped 'rolled' with fresh timestamps. When the phone finally syncs, its older done_at rows lose LWW. A whole week of reading history reads as unfinished — caused purely by the missing push-on-mutate/push-on-hide.

### D3. user_settings packs many independently-edited knobs and two arrays into one LWW row — concurrent different-field edits silently lose one side

- **Location:** `frontend/src/lib/services/settings.ts:100`
- **Mechanism:** saveUserSettings is read-modify-write of the whole singleton ({...existing, ...changes}), and conflict resolution is whole-row LWW. focus_tag_ids and strip_whitelist are arrays mutated in place by unrelated flows (PlanApp defaults, Settings link-handling, remapFocusTags after tag merges). The codebase explicitly split Link flags from Note prose to avoid exactly this (types.ts Link comment), but settings concentrates ~12 knobs in one row, so any two-device pair of edits to different settings within a sync gap resolves to one device's entire row.
- **Two-device scenario:** On A the user adds 'youtube.com' to the strip whitelist (row stamped t1). On B, before syncing, they add a focus tag (row stamped t2>t1). After sync B's row wins wholesale: the whitelist entry is gone on both devices with no indication.

### D4. Every sync re-downloads and locally rewrites all rows it just pushed (self-echo), inflating the reported pulled count and widening the clobber window

- **Location:** `frontend/src/lib/sync.ts:323`
- **Mechanism:** Push runs before pull and assigns the pushed rows seqs above lastPullSeq, so the same sync's pull pages return them; the LWW test `row.updated_at >= local.updated_at` (line 323) is true on equality, so each echoed row is re-put locally (line 324) and counted in `pulled` (line 325). Cost: a first sync of N rows transfers ~2N rows and performs N redundant writes; the Settings status line reports 'pushed N, pulled N' for a one-way upload; and every redundant put is one more instance of the finding-5 race window. Tracking the ids accepted this sync (already returned by the push response) or skipping equality-on-own-rows would eliminate it.
- **Two-device scenario:** Device A does its first push of 8000 rows to an empty server, device B hasn't synced yet. A's pull immediately re-downloads all 8000 rows and rewrites them locally while the user is actively triaging, and Settings reports 'pushed 8,000, pulled 8,000' — the user on A concludes device B's data was merged in and stops investigating why B's links are absent.
